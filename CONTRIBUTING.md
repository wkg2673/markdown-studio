## Getting Started

1. Fork the repo.
2. Clone your fork to your local machine:

   ```bash
   git clone https://github.com/YOUR-USERNAME/markdown-studio.git
   ```

4. Navigate to the project:

   ```bash
   cd markdown-studio
   ```

5. Create a new branch for your changes:

   ```bash
   git checkout -b feature/feature-name
   ```

You are now ready to start contributing!

## Reporting Bugs

If you find a bug, please open an issue in the GitHub repo.

Before creating an issue:
- Check whether the issue has already been reported.
- Make sure you're using the latest version.
- Provide as much relevant information as possible.

When reporting a bug, please include:

- A clear and descriptive title.
- A description of the problem.
- Steps to reproduce the issue.
- Expected & actual behavior.
- (Optional) Screenshots or recordings.
- Your OS and browser.

The more info you provide, the easier it will be fixed.

## Suggesting Features

Have an idea that could make Markdown Studio better? Feature suggestions are welcome!

When suggesting a feature:
- Explain what the feature should do.
- Describe the problem it would solve.
- Explain why it would be useful.
- Include examples or mockups if applicable.

Please check existing issues before submitting a new suggestion to avoid duplicates.

## Submitting Pull Requests

Pull requests are the primary way to contribute code to Markdown Studio.

Follow these steps:

1. Fork the repo.
2. Create a new branch from the latest dev branch.
3. Make your changes.
4. Test your changes thoroughly.
5. Commit changes with a descriptive commit message.
6. Push your branch to your fork.
7. Open a pull request against the original repo.

### Pull Request Guidelines

Please make sure your pull request:

- Has a clear and descriptive title.
- Explains what was changed and why.
- References related issues, if applicable.
- Includes screenshots (for visual changes).
- Does not introduce unrelated changes(f.e. changing a single line of code).
- Has been tested before submission.

Pull requests are reviewed and requested to make changes before being merged.

Please be patient while I'm reviewing your contribution.

## Code Guidelines

To keep the codebase maintainable and consistent, please follow these guidelines:

- Write clean, readable, and maintainable code.
- Use meaningful variable and function names.
- Keep functions and components focused on a single responsibility.
- Avoid unnecessary dependencies.
- Follow the existing project structure and coding conventions.
- Add comments when the code requires additional explanation.
- Test your changes before submitting a pull request.
- Avoid committing generated files, build artifacts, or sensitive information.

Consistency with the existing codebase is preferred over introducing entirely new conventions.

## Commit Messages

Please use clear and descriptive commit messages.

Some examples:

```text
feat: add document search
fix: resolve preview rendering issue
style: improve toolbar spacing
docs: update installation instructions
refactor: simplify editor state management
```

Recommended prefixes:

| Prefix | Description |
|--------|-------------|
| feat | New feature |
| fix | Bug fix |
| docs | Documentation changes |
| style | Styling and formatting changes |
| refactor | Code restructuring |
| test | Adding or updating tests |
| chore | Maintenance tasks |
